DATA RETRIEVED BY THE AUDIT-LOGS EYE BUTTON (.al-properties)
Last updated: 2026-09-15
Source: resources/views/audit-logs/index.blade.php
Page: http://127.0.0.1:8000/audit-logs

======================================================================
WHEN THE EYE SHOWS
======================================================================
- The button (class="al-eye-btn") is rendered only when the activity row's
  `properties` value is NOT empty:
      @if ($activity->properties && $activity->properties->isNotEmpty())
- Clicking it expands a row (class="al-properties") that displays the stored
  JSON via: json_encode($activity->properties->toArray(), JSON_PRETTY_PRINT)
- Coverage on the current database (98 activities):
      - 90 rows have non-empty `properties`  -> eye button is shown
      - 8 rows  have properties = []         -> NO eye button

- Rows WITHOUT the eye (properties stored as empty array []):
    * Approved user <name>
    * Changed user <name> status to approved / suspended
    * Force logged out device of <name>
  These activities were logged with ->log(...) and no event / no properties,
  so there is no JSON payload to view.

======================================================================
THE 5 DISTINCT DATA TYPES (properties JSON shapes)
======================================================================

----------------------------------------------------------------------
1) CREATED CITATION (event = created, subject = Citation)
   Example activity ids: 5, 6, 9, 10, 16, 25, 68, 77, 80
----------------------------------------------------------------------
{
  "attributes": {
    "id": <int>,
    "citation_number": "CIT-...",
    "violation_type_id": <int>,
    "issued_by": <int>,
    "penalty_amount": "<decimal>",
    "status": "issued",
    "location": "<string>",
    "notes": <string|null>,
    "issued_at": "<ISO datetime>",
    "due_date": "<ISO datetime>",
    "created_at": "<ISO datetime>",
    "updated_at": "<ISO datetime>",
    "vehicle_plate": "<string>",
    "vehicle_make": "<string>",
    "vehicle_model": "<string>",
    "vehicle_type": "<string>",
    "vehicle_color": "<string>",
    "driver_name": "<string>",
    "driver_license": "<string>"
  }
}
- Contains only "attributes" (the newly created citation / full row).

----------------------------------------------------------------------
2) CREATED PAYMENT (event = created, subject = Payment)
   Example activity ids: 12, 14, 17, 19, 21, 23, 26, 38, 41, 45,
                         47, 49, 52, 54, 56, 58, 60, 62, 64, 66,
                         69, 71, 73, 78, 81, 88, 90, 92, 96
----------------------------------------------------------------------
{
  "attributes": {
    "id": <int>,
    "receipt_number": "RCP-...",
    "citation_id": <int>,
    "cashier_id": <int|null>,
    "amount": "<decimal>",
    "payment_method": "<string>",
    "reference_number": <string|null>,
    "notes": <string|null>,
    "paid_at": <ISO datetime|null>,
    "created_at": "<ISO datetime>",
    "updated_at": "<ISO datetime>",
    "paymongo_checkout_id": <string|null>,
    "paymongo_payment_intent_id": <string|null>,
    "paymongo_status": <string|null>,
    "online_payment_method": <string|null>,
    "paymongo_session_ids": <array|null>
  }
}
- Contains only "attributes" (the newly created payment / full row).

----------------------------------------------------------------------
3) UPDATED PAYMENT - PAYMONGO / ONLINE-PAYMENT FLOW
   (event = updated, subject = Payment, described as "updated")
   Example activity ids: 20, 22, 24, 27-36, 40, 42-44, 46, 48,
                         50, 51, 53, 55, 57, 59, 61, 63, 65, 67,
                         70, 72, 74, 79, 82-87, 89, 91, 93
----------------------------------------------------------------------
{
  "attributes": {
    "updated_at": "<ISO datetime>",          <- present when the flow
    "paymongo_checkout_id": "<string>",       changes checkout ids
    "paymongo_status": "active|cancelled|paid",  <- payment status
    "paymongo_session_ids": ["cs_...", ...],  <- grows as checkouts are
    "paymongo_payment_intent_id": "<string>",   created for the payment
    "paid_at": "<ISO datetime>",
    "online_payment_method": "gcash|qrph|..."
  },
  "old": {
    ... the same fields with their PREVIOUS values ...
  }
}
- Only the fields that actually changed are present in "attributes"; their
  previous values are stored under "old".
- The PayMongo checkout flow updates a payment many times (each new checkout
  adds a session id to paymongo_session_ids), so a single payment can produce
  several "updated" rows in the audit log.

----------------------------------------------------------------------
4) UPDATED - MARKED AS PAID
   (event = updated, subject = Payment or Citation, described as "updated")
   Example activity ids: 13, 15, 76, 95
----------------------------------------------------------------------
{
  "attributes": {
    "status": "paid",
    "updated_at": "<ISO datetime>"
  },
  "old": {
    "status": "issued",
    "updated_at": "<ISO datetime>"
  }
}
- Recorded when a payment completes successfully (PayMongo webhook) and the
  citation status flips issued -> paid. Only status + updated_at change.

----------------------------------------------------------------------
5) DELETED PAYMENT (event = deleted, subject = Payment)
   Example activity ids: 18, 37, 39
----------------------------------------------------------------------
{
  "old": {
    "id": <int>,
    "receipt_number": "RCP-...",
    "citation_id": <int>,
    "cashier_id": <int|null>,
    "amount": "<decimal>",
    "payment_method": "<string>",
    "reference_number": <string|null>,
    "notes": <string|null>,
    "paid_at": <ISO datetime|null>,
    "created_at": "<ISO datetime>",
    "updated_at": "<ISO datetime>",
    "paymongo_checkout_id": <string|null>,
    "paymongo_payment_intent_id": <string|null>,
    "paymongo_status": "active|...|<null>",
    "online_payment_method": <string|null>,
    "paymongo_session_ids": <array|null>
  }
}
- Contains ONLY "old" (the full deleted payment's last state); there is no
  "attributes" key because the record no longer exists.

======================================================================
SUMMARY TABLE
======================================================================
Event tag  | Subject        | JSON shape                | Eye?
-----------|----------------|---------------------------|-----
Created    | Citation       | attributes (full row)     | yes
Created    | Payment        | attributes (full row)     | yes
Updated    | Payment        | attributes (changed) +    | yes
           |                | old (previous values)     |

(null)     | User           | []                        | NO
Approved/  |                |                           |
status     |                |                           |   (approvals, status
change /   |                |                           |    changes, force
force      |                |                           |    logout have no
logout     |                |                           |    eye button)

======================================================================
NOTES
======================================================================
- All user-approval / status-change / force-logout activities (liked by
  UserController.php ->log() calls) store `properties = []`, which is why
  their rows do not display the eye button or any expandable JSON.
- Values are the raw model attributes captured at log time; they are not
  re-read from the database, so deleted/edited records keep their snapshot.
