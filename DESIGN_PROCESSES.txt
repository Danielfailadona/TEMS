 USE CASE DIAGRAM — OVERVIEW
═══════════════════════════════════════════════════════════════════════════════════

 The Use Case Diagram for TEMS identifies five actors — Admin, Enforcer, Front
 Desk, Cashier, and Citizen — and maps 25 use cases (UC-TEMS-001 to
 UC-TEMS-025) that define the system's behavioral boundaries. Three base cases
 (Manage Operations, Manage Monitoring, and Manage Administration) act as
 primary containers, each «including» specialized View* use cases. The diagram
 captures the complete interaction surface of the system, making it clear how
 each user group accesses system capabilities and how internal operations
 depend on shared viewing functions.

 DESIGN OF SOFTWARE — SYSTEM PRODUCT PROCESSES
═══════════════════════════════════════════════════════════════════════════════════

 This section describes how the TEMS will be planned and designed prior to
 development. It depicts how various components of the system will interact,
 including how users will interact with the system, how data will be organized,
 and how each process will be designed. To better understand how various system
 behaviors will interact, tools such as Use-Case Diagram, Use-Case Description,
 Entity Relationship Diagram (ERD), and Data Dictionary were used. The above tools
 are employed to ensure that the system will function properly, meet user
 requirements, and manage data at various processes of the system.


 2. ENTITY RELATIONSHIP DIAGRAM (ERD) — OVERVIEW
 ────────────────────────────────────────────────────────────────────────────────
 The Entity Relationship Diagram for TEMS defines 20 database tables and their
 interconnections, forming the structural backbone of the system's data layer.
 Each entity maps to a table documented in the Data Dictionary using the
 reference format: Field Name | Data Type | Data Format | Field Size |
 Description | Example. Primary keys enforce entity identity; foreign keys
 enforce referential integrity across actor-driven workflows.

 Core entities include the central users table (referenced by 13 child tables
 via user_id FKs), the violations-and-citations cluster (violation_types ->
 citations -> evidence/appeals/payments/clamping), and supporting tables for
 teams, zones, notifications, enforcer-location tracking, audit logging, and
 session management. A polymorphic archives table snapshots major records, and
 a team_user pivot supports many-to-many assignments.

  4. SOFTWARE DESIGN APPROACH
  ────────────────────────────────────────────────────────────────────────────────
  The design of TEMS follows a structured, iterative software engineering approach
  grounded in the Model-View-Controller (MVC) architecture. Each phase below maps
  inputs from prior documentation requirements (USE_CASE_NARRATIVES.txt,
  REQUIREMENTS_ANALYSIS.txt, DATA_DICTIONARY.txt) to concrete outputs, ensuring
  that every system behavior is traceable to a documented requirement.


  5. DESIGN PROCESS MODEL
  ────────────────────────────────────────────────────────────────────────────────

  Phase 1: Requirements Understanding
    Requirements are drawn from the use case narratives (UC-TEMS-001 to
    UC-TEMS-025), the requirements analysis, and non-functional constraints
    (performance, security, scalability). Each actor interaction is validated
    before design proceeds.

  Phase 2: Architectural Design
    TEMS adopts a 3-tier MVC architecture: Presentation (Blade views + Tailwind
    CSS), Application (controllers and service layers), and Data (Eloquent
    models and database migrations). RESTful API boundaries and role-based
    authorization (Laravel Sanctum + Gates) are defined at this phase.

  Phase 3: Component Design
    Responsibilities are assigned per actor:
      • Admin      — user management, archive operations, system dashboards
      • Enforcer   — citation issuance, location tracking, evidence capture
      • Front Desk — vehicle release coordination, citizen encounter logging
      • Cashier    — payment validation and recording
      • Citizen    — public portal (citation lookup, appeals, clamping requests)
    «include» relationships identified in the UML diagram are codified as
    reusable service classes (citation creation includes evidence capture,
    location tracking, and notification in a single transaction).

  Phase 4: Interface & Data Design
    Wireframes are translated to Blade templates. The database schema (20
    database tables) is created through Laravel migrations; all fields,
    types, sizes, and constraints are documented in the Data Dictionary.
    API responses are standardized using Laravel API Resources.

  Phase 5: Quality Design
    Unit and feature tests are written with PHPUnit per actor workflow.
    Authorization tests verify Gate and Policy coverage. Seeder and factory
    strategies ensure reproducible test data.

  Phase 6: Iteration & Enhancement
    Feedback is gathered from stakeholders and incorporated in iterative
    cycles. Version control (Git) and release branching support both
    hotfix and feature development.


  6. SYSTEM PRODUCT PROCESSES
  ────────────────────────────────────────────────────────────────────────────────

  A. Database Engineering Process
     The schema is derived from entity-relationship reasoning applied to the
     use cases. Every table is versioned via migrations, with rollback
     support. Foreign-key delete behaviors (CASCADE, SET NULL, RESTRICT) are
     chosen per actual usage pattern, and baseline seeders establish default
     roles, violation types, and zones.

  B. Authentication & Authorization Process
     Laravel Sanctum provides token-based API session management. The role
     enum (SuperAdmin, Administrator, Enforcer, ClampingOfficer, Cashier,
     FrontDesk, VehicleOwner) is enforced at both the Eloquent model scope
     and the Gate layer. Passwords are hashed with bcrypt; Supabase OAuth
     (supabase_id column) supports an optional external identity provider.

  C. Notification Process
     Notifications are event-driven: domain events dispatch queued jobs that
     create database records, broadcast real-time updates, and send e-mail
     alerts. Templates define type, title, message, and payload structure;
     read-state is tracked per user, with automated archiving after 90 days.

  D. Spatial / Location Tracking Process
     Enforcer latitude, longitude, and GPS accuracy are logged per shift.
     This data supports evidence-of-correctness audits and supervisor
     monitoring dashboards.

  E. Audit & Archiving Process
     The activity_log table captures who acted on what (causer, subject,
     properties batch) for every significant action. A polymorphic archives
     table stores snapshots of important records (citations, appeals,
     payments) with reason and archiver identity, enabling full history
     replay even after soft-deletion or modification.

  F. Reporting & Analytics Process
     Saved Searches model stores user-defined filter criteria. Aggregations
     over citation, payment, and appeal data are scoped by zone and date
     range, with server-side PDF and Excel exports for regulatory reporting.


  7. DESIGN PRINCIPLES APPLIED
  ────────────────────────────────────────────────────────────────────────────────
  Separation of Concerns — Controllers remain thin; business logic lives in
    service classes.  Convention over Configuration — Laravel defaults
    minimize bespoke framework plumbing.  Fail-fast on Integrity — Database-
    level constraints and Eloquent casts enforce correctness early.
    Reusable Components — Blade components and modular Livewire widgets reduce
    duplication.  API-first for Integrations — Front Desk and Citizen portals
    consume the same API layer consumed by internal tools.  Security by
    Default — HTTPS, CSRF tokens, validated FormRequest classes, and mass-
    assignment guards are standard.


  8. DEPLOYMENT & OPERATIONS PROCESS
  ────────────────────────────────────────────────────────────────────────────────
  Development   → Windows / XAMPP on localhost for prototyping
  Staging       → Same-stack mirror seeded with production-scale sample data
  Production    → Linux (Ubuntu + Nginx + PHP-FPM + MariaDB)
  CI/CD         → GitHub Actions pipeline: lint → test → build → deploy
  Monitoring    → Laravel Horizon for queue visibility; log aggregation
                   via Papertrail or equivalent.  Backup → Nightly mysqldump
                   for transactions; weekly filesystem copy for citation
                   evidence images.


  9. DESIGN DECISIONS & TRADE-OFFS
  ────────────────────────────────────────────────────────────────────────────────
  Decision: Laravel MVC → Pros: rapid iteration, mature ecosystem,
    developer familiarity.  Cons: opinionated structure, PHP dependency.
  Decision: JSON columns for notification payloads → Pros: flexible schema,
    fast reads.  Cons: limited ad-hoc querying; mitigated by using
    JSON_CONTAINS / JSON_EXTRACT where needed.  Decision: Polymorphic
    archive table → Pros: single table captures all entity types, uniform
    API.  Cons: looser type safety; mitigated by cascading validation in
    model event observers.  Decision: Client device tracking →
    Pros: per-login audit trail.  Cons: PII stored (device name, IP);
    mitigated by encrypting IP addresses at rest.


  10. VERIFICATION OUTCOMES
  ────────────────────────────────────────────────────────────────────────────────
  The design outputs are traceable back to the documented artifacts:
    Use-Case Diagram     → Defines actor boundaries and «include» relationships
                            (reflected in reusable service flows).
    Use-Case Narratives  → Detailed step-by-step actor interactions driving
                            controller method design.
    ERD / Migrations     → Primary/foreign key structure enforced at the
                            database level; matches entities in Data Dictionary.
    Data Dictionary      → Complete field catalog ensuring consistent naming,
                            typing, and sizing across the system, serving as
                            the single source of truth for data-related design
                            decisions.
  Together, these artifacts confirm that TEMS is designed to function
  correctly, fulfill every user requirement, and manage data consistently
  across all processes.
